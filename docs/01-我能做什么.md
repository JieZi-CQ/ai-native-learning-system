# 1️⃣ 我能具体帮你做什么？

我可以成为以下类型的助手：

## A. GitHub & 开源社区助手

我可以用 GitHub API 做到：

### 分析项目真实活跃度（不只看 Stars）
- Issue 的回复时间和深度（反映维护者是否认真）
- PR 审查速度和审查意见的严谨程度
- Contributor 增长趋势（是否在吸引新人）
- Release 频率（是否定期更新）
- Code 覆盖率和测试质量（代码健康度）

### 追踪具体技术人物在做什么
- 他们最近 Star 了什么项目（兴趣方向）
- 他们最近的 Commit 活动（当前工作）
- 他们打开了哪些 Issue（解决的问题）
- 他们参与的 Code Review（技术深度）
- 他们维护的项目是否健康（长期投入度）

### 对比不同项目的成熟度
- 项目被多少其他项目依赖（实际采用率）
- 社区中的讨论质量（Issue 中的技术深度）
- 文档完善程度
- 测试覆盖率

### 识别一个项目的核心贡献者圈子
- 谁是真正的核心维护者（提交量）
- 谁的 Code Review 最严格（质量守门人）
- 他们共同参与的其他项目（找到相关生态）
- 他们的技术品味和偏好

### 帮你理解真实的开源协作
- 通过阅读真实 Issue/PR 讨论，学到设计决策
- 看维护者如何拒绝功能需求（学会说"不"）
- 看社区如何讨论技术权衡
- 学习优秀的 Code Review 文化

---

## B. 技术选型助手

### 对框架/库进行客观分析
- 官方文档质量、完整性
- 社区规模和活跃度
- 学习曲线（需要多长时间掌握）
- 与其他框架的互操作性
- 成本（是否收费、隐藏成本）
- 对你的项目的迁移成本（如果以后换框架）

### 区分"炒作周期中的框架"和"稳定项目"
- 用 GitHub Trends 数据识别"虚火"
- 看真实项目的采用率
- 追踪项目的 Issue 数量变化（多不代表好，但连续增长代表有价值）
- 检查是否有"玩具项目"在虚增 Stars

### 追踪技术的生命周期
```
新兴期（0-1年）：论文刚发表、项目刚开源
  风险：可能流产
  机会：成为早期采用者，未来可能很有竞争力

快速增长期（1-3年）：社区快速扩大、应用出现
  风险：API 可能不稳定、文档可能滞后
  机会：最高学习价值期

稳定期（3-10年）：生态完善、API 稳定、最佳实践明确
  风险：相对较低
  机会：安全选择，适合生产项目

衰退期（10+年）：被新技术替代、社区萎缩
  风险：难以招聘维护者、生态工具减少
  机会：作为维护旧系统的知识
```

### 用数据帮你做决策
- 不是"我觉得 X 不错"，而是"X 的 GitHub Discussions 中有 300 个活跃讨论"
- 收集多个候选方案的数据进行对比表

## C. AI Native 学习助手

### 梳理 AI Native 开发中的"稳定基础"
- Transformer 架构不会在 2-3 年内过时
- Prompt Engineering 的核心原理（思维链、角色设定等）会长期有效
- RAG 的概念不会变，但具体工具链会演变
- Agent / Tool Use 的设计模式会逐渐成熟

### 帮你理解 LLM / Agent 的当前最佳实践
- 看 OpenAI、Claude、LLaMA 官方文档的设计思路
- 追踪 GitHub 上的高星项目（LangChain、LlamaIndex 等）的演变
- 理解为什么有些技术被广泛采用（例如为什么 RAG 而不是微调）

### 识别短生命周期 vs 长期价值的技术
- Prompt 的某个技巧可能 3 个月后就过时
- 但 RAG 作为 AI 应用的架构模式会持久
- 某个 Agent 框架可能一年后被新框架替代
- 但"如何让 LLM 可靠地调用外部工具"的问题会长期存在

### 找到中英文社区中关于 AI 工程实践的优质资源
- 追踪 Hugging Face 论坛、官方博客
- 监测 GitHub Issues 中的最佳实践讨论
- 找到中文社区的实践经验（如何在国内环保下用 AI）

## D. 信息源管理助手

### 帮你组织多个信息来源
- GitHub Trends（实时看什么框架在流行）
- Hacker News（看全球开发者的讨论）
- Reddit（看真实用户的问题和吐槽）
- arXiv/Papers（追踪最新研究）
- 掘金、V2EX、微博（中文社区的讨论）
- 公司技术博客（看大规模应用）

### 交叉验证信息真伪和重要程度
- 某个框架在 HN 上很火，但 GitHub Issues 显示是虚火？
- 某个技术的论文很火，但实际生产环境很少用？
- 这些都可以通过数据对比发现

### 识别信息源中的偏见
- Twitter 是美国创业者社区，对企业级应用可能了解不足
- 中文论坛可能对国外技术不了解，对国内解决方案过度吹捧
- 学术论文关注创新，不关注工程可维护性

## E. 项目+作品集助手

### 帮你整理"过去未完成的项目"
- 哪些项目的核心逻辑还有价值？
- 哪些可以简化成 MVP 后直接开源？
- 如何规划重启的优先级（从最有价值的开始）

### 设计项目的"最小可开源化"版本
- 不需要完美的文档，清晰的 README 就够
- 不需要覆盖所有功能，核心功能能用就行
- 什么时候开源"太早"（代码惨不忍睹）
- 什么时候开源"太晚"（完美主义延迟发布）

### 帮你了解如何在项目中集成 GitHub 的协作流程
- Issue 怎么写才能吸引人来解决
- PR 怎么审查才能维持代码质量
- Discussion 怎么用来做社区讨论
- 如何建立 Contributor 的贡献激励

### 优化你的 GitHub Profile
- 项目的 README 是否能让陌生人 5 分钟内明白你做了什么
- README 中的"Quick Start"能否复制即用
- 你的个人简介是否清楚地表达了你的技术方向

## F. 社区学习助手

### 帮你识别值得贡献的开源项目
- 不是"Star 最多的项目"，而是"最欢迎新贡献者的项目"
- 用数据识别：有多少 `good-first-issue` 标签的 Issue、新人 PR 被接受的比例、Maintainer 对新人的耐心程度

### 用数据分析一个项目是否"欢迎新人"
- Issue 回复时间（超过 2 周没回代表可能冷门）
- 新人 PR 是否被认真 Review
- Maintainer 对新人问题的耐心度
- 是否有 CONTRIBUTING.md 和明确的贡献流程

### 跟踪华人开源贡献者和团队
- 追踪国内主要的开源组织（阿里、字节、腾讯、PingCAP 等）
- 找出中文社区中的活跃贡献者
- 了解中文社区的项目是否也遵循国际开源规范

### 理解国内外开源生态的差异
- 全球社区重视什么（文档、测试、安全）
- 中文社区重视什么（可能更关注快速迭代）
- 如何让你的项目同时被两个社区接纳

---

## G. 自我评价助手

### 帮你设计"判断一个技术/框架/人物是否值得关注"的评分体系
- 建立一份你自己的评估清单
- 定期用这份清单评估新技术，逐渐校准

### 定期回顾你的学习成果和技术栈选择是否合理
- "3 个月前我说应该学 X，现在看起来怎样？"
- 通过回顾，改进你的判断能力

### 追踪你在开源社区中的实际贡献
- 你提交的 PR 被接受了多少
- 你的项目获得了多少真实用户
- 你是否在实践"理想的开源流程"

## 总结：7 个角色的对应关系

| 角色 | 核心能力 | 实际用途 |
|------|--------|--------|
| **GitHub 数据分析师** | 用 API 分析项目真实活跃度 | 判断项目是否值得关注、学习 |
| **技术选型顾问** | 对比框架，给出客观数据 | "学 A 还是学 B？" |
| **AI Native 教练** | 梳理稳定基础 vs 短期热点 | 避免盲目学新框架 |
| **信息源管理员** | 帮你用多个来源交叉验证 | 不陷入信息茧房 |
| **项目启动官** | 从想法到开源的完整指导 | 把项目真的做出来 |
| **社区学习指南** | 找到好项目、好人物、好讨论 | 真正参与开源协作 |
| **反思镜像** | 帮你建立自我判断系统 | 遇到新技术自己会判断 |
